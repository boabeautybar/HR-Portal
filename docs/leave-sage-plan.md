# Leave Hub ↔ Sage Payroll Professional — Integration Plan

**Status: 🟢 ANNUAL LEAVE LIVE (built, not yet deployed). Updated 2026-07-17.**
This doc now covers only what's actionable — **annual leave**. Everything that needs Sage-
consultant data or a per-type report (Phase 0 checklist, per-type balances, the Sage batch
export, HCSBC council data, the future API) is split into **`docs/leave-parked.md`**.

Goal: the hub is the single accurate **annual-leave** surface — balances the hub computes
itself from the durable anchor, validation at application time (including *forward* projection
to a future leave date), a guided 3-step approval wizard, and use-it-or-lose-it expiry alerts.

**Scope cut (2026-07-17, owner):** only annual leave is actioned here; all other leave types
are parked (`leave-parked.md`) until the Sage information lands.

### Accrual model change (2026-07-17) — 25th-cycle → start-date anniversary

Accrual **no longer** credits 1.25 days on the 25th for everyone. It now credits **1.25 on each
person's monthly start-date anniversary** (started the 10th → a credit every 10th; a 31st start
clamps to each month's last day). Consequences:

- Balances tick up on **different days per person** — "the balance updates daily across the
  roster," which the 25th model couldn't show.
- The first credit lands **one month after** the contract/onboarding start (you accrue *after*
  working a month), never on day one.
- `annualBalanceFor()`, the Leave Balances tab's `computeRow`, the approval wizard and the
  expiry radar all run this one model (`accruedLeaveFor` / `anniversariesBetween`); a missing
  `start_date` (seed-only managers) falls back to the old 25th cycle and is flagged in the UI.
- **`balanceStaleness` deliberately stays on the 25th payroll clock** — it measures Sage-upload
  freshness, not accrual, so it must not move to the anniversary model.
- The next Sage upload re-anchors and absorbs any drift the model change introduces.
- Proven by `scripts/check-leave-codes.js` §5 (accrual: month-end clamps, first-credit-after-
  start, anchor-excluded) and §6 (expiry cycles/deadline/red boundary).

Legend: ⬜ not started · 🔨 in progress · ✅ done · ⏸ parked (`leave-parked.md`)

## 0. The reality check that shaped this plan

**Sage Business Cloud Payroll Professional (SBCPP — our product, VIP lineage) has no public
REST API.** The original intent was "start with GET requests" — that is not possible on this
product:

- Sage SA's own knowledge base states the VIP-lineage products do not support third-party API
  integrations and directs integrators to the in-app **batch import/export utilities**.
  (za-kb.sage.com solution 220822120315733)
- The "Sage Payroll API" on developer.sage.com is a **different product** (UK/Ireland
  small-business payroll) — not SA Payroll Professional.
- A true REST API only exists on **Sage 300 People** (self-hosted, API-key auth) — i.e. a
  payroll migration, not an integration setting.

**So the plan is file-based, using Sage's officially supported paths:**

| Direction | Mechanism |
|---|---|
| Sage → hub ("GET") | **Leave-balance report export** (xlsx/csv from Sage's History/Standard reports), uploaded to the hub monthly after each payroll run |
| Hub → Sage ("push") | **Leave Transaction Batch file** — Sage's official fixed-width `.TXT`/`.ASC` import format, generated by the hub for download (§Phase 4) |

Decisions locked with the owner: file-based approach · sync cadence **monthly after each
payroll run** (currently ad-hoc — plan includes staleness display + upload reminder) ·
balances shown as **projected** (last Sage figure adjusted for what Sage doesn't know yet) ·
council = **HCSBC** (hairdressing).

## 0.5 Hub-anchored mode (2026-07-16) — Phase 0 de-blocked

Getting consultant answers is slow, so the plan no longer waits for them. **The anchor
already exists in prod**: the last balance upload is saved in Supabase app_state
(`boa_leave_balances_v1`) — **asOf 2026-06-25 (the current cycle start), 493 employees with
opening balances, uploaded 2026-07-14 by Justin Rule** (verified live 2026-07-16). From that
anchor the hub computes annual balances itself:

> **balance = opening (asOf) + 1.25 days per completed 25th→24th cycle − annual leave taken
> on the calendar since asOf** — exactly the math `availableForEc`/LeaveBalancesTab already
> runs today. The anchor makes it authoritative rather than advisory.

Consequences for the phases:

- **Sage report uploads become re-anchor + reconciliation events, not a dependency.** Each
  future upload replaces the anchor and reports drift between Sage's figure and the hub's
  computed figure per employee (pulls Phase 4.4's reconciliation idea forward).
- **Only Phase 4 (the batch export file) hard-blocks on Phase 0** (company number, EC map,
  leave lines, layout verification). Everything else starts now with defaults/placeholders.
- **New first task (Phase 2.0): make the anchor durable.** `boa_leave_balances_v1` is
  overwritten by the next upload — copy the current value into an append-only openings
  snapshot (`boa_leave_openings_v1`: array of `{asOf, savedAt, source, uploadedBy, entries}`)
  so the starting point can never be silently destroyed; optionally also park the original
  `.xlsx` in the `staff-uploads` bucket for audit.
- **Known approximation, flagged in the UI:** sick / family / maternity have no Sage opening
  figure yet. Sick counting starts from hub attendance history (`sick_n`/`sick` marks; BCEA
  30-per-36-months for non-members, HCSBC 66-per-3-years for members) and is labelled
  "hub-estimated" until a per-type Sage report reconciles it. Annual is the accurate one from
  day one; the others tighten when Phase 0 eventually lands.
- Phase 5's cycle anchor defaults to **engagement anniversary** (`staff.start_date` — the
  BCEA default) until 0.7 confirms otherwise.

| Reminder pattern | `pubCycleAlert` dashboard card (Owner + National Ops gating) | Clone for "upload the Sage balance report" nag |

### How leave is *coded* today (the problem)

- Grid cells: `L` = **all** leave generically, `ML` = maternity, `X` = legal/unpaid band,
  EL = render-only overlay for `emergency:true` records. The grid does NOT know annual vs sick
  vs family.
- `boa_leave_v1.type` is effectively always "Annual leave" + an `emergency` boolean.
- Attendance codes: `sick_n` (paid sick + note), `sick` (unpaid, no note), `frl`, `absent`, `no`.
- Sage wants one letter per transaction: `A`nnual / `F`amily / `S`ick / `M`aternity / custom `a–z`.

Four vocabularies, no single mapping → Phase 1 fixes the coding before any data flows.

## Phase 1 — Leave coding normalization 🔨 (1.1/1.2/1.4 built 2026-07-16, not yet deployed)

**Built:** `LEAVE_CODES` + `canonicalLeaveType()` / `canonicalFromRequest()` / `isPaidAnnualRec()`
/ `sickModelFor()` in app.jsx; `boa_sage_config_v1` accessors in data.js;
`scripts/check-leave-codes.js` gates it (244 live records replayed, 0 changed answers).

**⚠ The `type` freeze — read before touching planner records.** `type: "Annual leave"` is not a
label, it's a load-bearing literal: 12+ consumers across **all three deployed sites** key on it
to mean "this person is away" (`kiosk/data.js:541` and `:607`, My BOA schedule overlay, the
attendance sheet, Fresha blocks, the planner UI). Vary it and those surfaces silently stop
seeing the leave. So `plannerTypeCompat()` writes the frozen literal for every type, and
**`leaveType` carries the truth**. Letting `type` vary = a separate migration: move those
consumers to `canonicalLeaveType()` first, then unfreeze (checker enforces the freeze until then).

**Live bug this closed:** both calendar-write paths hardcoded `type: "Annual leave"`, and the
balance math charged annual days for anything on the planner. The leave board accepts every
type except Sick/Absent, so the first family-responsibility or unpaid approval would have
silently eaten annual days someone never took. Balance math now asks `isPaidAnnualRec()`
(canonical), which is provably identical on all 244 existing records and correct for the rest.

**Deliberately NOT stored: a `days` count on the record.** Without a schedule cache
`leaveDayBreakdown` only *estimates* off-days (`fromSchedule:false`), and the schedule can change
after approval. Chargeable days get computed against the published grid at export time (Phase 4)
— never estimated at approval and then trusted by Sage.

Remaining in this phase: **1.3** (My BOA forms submitting the canonical set incl. Maternity) —
⏸ **parked** (`leave-parked.md`); the portal-side approval wizard already writes `leaveType`
canonically, so this is a My BOA form-label refinement, not a data-integrity gap.

Make one canonical vocabulary so data can be grabbed/pushed without translation guesswork.

**1.1 One canonical code table.** A single constant mapping every vocabulary
(app.jsx + anywhere else that needs it; only mirror as a `leave-codes.js` file à la
`shift-rules.js` if kiosk/My BOA actually consume it — start portal-only):

| Canonical | Sage letter | Grid cell | Attendance | Paid? |
|---|---|---|---|---|
| Annual | `A` | `L` | — | paid |
| Sick (note) | `S` | `L` | `sick_n` | council: fund / non-council: paid |
| Sick (no note) | `?` placeholder (0.3) | `L`/`X` | `sick` | unpaid |
| Family responsibility | `F` | `L` | `frl` | paid |
| Maternity | `M` | `ML` | — | unpaid (UIF/fund) |
| Unpaid / emergency (EL) | `?` placeholder (0.3) | `X` + EL overlay | `absent` | unpaid |

Unknown Sage letters are stored as `?` placeholders — harmless everywhere except the Phase 4
export, which refuses to emit rows whose canonical type still has a placeholder letter.

**1.2 Extend `boa_leave_v1` records** (additive, back-compatible — old records default to
Annual): `leaveType` (canonical), `days` (actual, from `leaveDayBreakdown`; fractional halves
allowed — Sage accepts fractions), `reason` (AN4), `sage: {exportedAt, batchRef}` stamp.

**1.3 Extend request forms.** My BOA leave/absence forms submit the canonical set
(Annual/Sick/Family/Maternity/Unpaid) instead of Annual/Sick/Absent; `leave_requests`
already has the column — no SQL change.

**1.4 New config key `boa_sage_config_v1`**: `{companies: {"001": {name}}, ecMap:
{<portalEc>: {company, sageCode}}, reasonCodes, leaveLines}` — filled from Phase 0. If Sage
codes == portal ECs, `ecMap` stays empty and the derivation rule (strip dash / pad to 8) is
documented in the key itself.

**1.5 Grid cells stay display-only.** `L`/`ML`/`X` don't gain per-type letters — that would
ripple through all four schedule surfaces. The planner record is the data source for Sage.

## Phase 3.6 — 3-step approval wizard ✅ (2026-07-17)

The one-click "Operationally clear" button let National Ops approve past the operational and
balance cautions without registering them. Replaced on the Leave Requests board with a single
**"Approve — review & confirm"** that opens `LeaveApprovalWizard`:

1. **Operations** — the clash verdict (`assessLeaveOps`) + overlap check (`findLeaveOverlaps`).
   If an already-approved leave overlaps, a **"Reverse this & continue"** button removes it
   (shared `clearTechScheduleLeaveGrid` — unstamps schedule + published snapshot) so the new
   request can take its place.
2. **Balance** — current balance **and**, for future leave, the projection to the leave's start
   date with the calculation spelled out (`opening + N anniversaries × 1.25 − booked = available`).
   Short-even-at-the-date offers the paid/unpaid **split** (`computeSplitPlan`).
3. **Review & complete** — one summary; only here does it write both gates + `finalizeLeaveIfReady`
   (planner record + `set_leave_status` approved + activity log), or the split path.

The **wizard replaces both gates** (owner decision): one approver walks all three steps.
`PayrollInboxTab` keeps the old two-gate flow as a secondary path (shared `finalizeLeaveIfReady`).
The **manual Leave Planner** entry (`addLeave`) opens the same wizard in a read-only
"review & confirm" mode — the record is validated + built first, and only persisted on completion.
No employee push channel exists in this codebase (My BOA is pull) — none was invented.

## Phase 5 — Expiry radar (use-it-or-lose-it) ✅ (2026-07-17)

There's no payout for unused annual leave, so expiring days must be *taken*.

- **Rule**: leave earned in an employment-year cycle forfeits **6 months after that cycle ends**
  (`LEAVE_EXPIRY_MONTHS`), the BCEA/HCSBC model — **every** completed employment year, not just
  the first. `annualLeaveCycles(startDate, today)` returns each completed cycle still inside its
  redemption window (`{cycleStart, cycleEnd, deadline}`); the anchor is the person's `start_date`
  anniversary until 0.7 confirms otherwise.
- **Days at risk** (`leaveExpiryForPerson`): balance vested by the cycle's end − paid annual
  leave booked in the redemption window (future bookings rescue at-risk days), capped at the
  person's current projected balance, consumed **oldest-cycle-first (FIFO)** so the total never
  exceeds what they still hold. **RED = ≤3 months** to the deadline (`LEAVE_EXPIRY_RED_MONTHS`).
- **Surfaces**: a "Leave expiring" panel on the Leave Balances tab (amber = in the window, RED =
  ≤3 months); a **dashboard alert** for HR + National Ops (`canSeeIncidents`); and — **once per
  employee per deadline** (dedup ledger `boa_leave_expiry_alerts_v1`) — an **auto-filed HR
  incident report** (`submit_incident_report` via new `data.js` `submitIncidentReport`) with the
  person, days, deadline and cycle. FRL keeps its anniversary reset; sick cycles are out of scope.
- Proven by `scripts/check-leave-codes.js` §6 (cycle window / deadline / RED boundary) and the
  `check-projection.js` FIFO fixture.

## Open questions / risks

- **Phase 4 hinges on Phase 0** (the rest no longer does, per §0.5) — keep chasing the
  consultant; the sample balance report (0.4) and the code-mapping answer (0.2) are the two
  items that unblock the most.
- Hub-estimated sick/family balances are only as complete as the hub's attendance history —
  anyone whose sick days predate the kiosk/attendance rollout is under-counted until a Sage
  figure reconciles them. The "hub-estimated" label carries this caveat.
- The From-Date column boundary in Sage's PDF (suspected typo) must be verified before any
  live import — a one-column shift would corrupt every date in the batch.
- The Sage community suggests council setup may be unavailable on some cloud tiers — if SBCPP
  can't model HCSBC natively, fund-sick may need a custom leave letter (0.6 decides).
- Cadence risk: projected balances are only as good as the monthly upload habit — the 2.4
  reminder is the mitigation, but a skipped month degrades gracefully (staleness warning, not
  wrong numbers presented as fresh).
